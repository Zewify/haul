# Haul — design

Haul (working name) is a Mac download manager in the mould of Internet Download Manager: a browser extension hands downloads to a native app, which fetches them over several connections at once, resumes them after a pause or a dropped line, and queues them.
It is a Zewify product, free with a one-time Pro unlock.

## Decisions (brainstorm, 2026-10-13)

The owner chose the first four; the rest are the recommendations they delegated before going to sleep, and each is open to change.

- **A Zewify product for Mac.** Native Swift, same shape as TickThock and VoxMorph.
- **Two editions from one codebase.** The *store* edition on the Mac App Store does segmented downloads, queueing and browser capture.
  The *direct* edition, sold from zewify.com and signed with Developer ID like VoxMorph, adds the video grabber: media and HLS streams found on a page.
  The grabber is kept out of the store edition because Apple rejects apps that download from video sites (Guideline 5.2.3).
- **Safari and Chromium in 1.0.** One WebExtension codebase: packaged inside the app as a Safari Web Extension, and listed once on the Chrome Web Store for Chrome, Edge, Brave, Arc and Vivaldi.
  Firefox waits for a user to ask.
- **A main window plus a menu bar item.** A regular app with a Dock icon and a window holding the download list; a menu bar item shows overall progress so the window can stay closed.
  Closing the window does not quit the app, because the extension needs it running.
- **The extension talks to the app over a local HTTP server** on `127.0.0.1`, not native messaging.
  A sandboxed app cannot write Chrome's native-messaging host manifest, and one transport serves both browsers and both editions.
  Pairing is a one-click approval in the app, not a copied key.
- **Free:** browser capture, up to 4 connections per download, 2 downloads at a time, pause, resume, queue, history.
  **Pro:** up to 32 connections per download, 8 downloads at a time, the speed limiter and the scheduler (both after 1.0), and in the direct edition the video grabber.
- **Ask before starting is on by default**, like IDM: a small panel shows the filename and folder with Start focused, so Enter accepts it.
- **Downloads land in `~/Downloads`** through the sandbox's Downloads entitlement; any other folder is chosen once in an open panel and kept as a security-scoped bookmark.
- **Nothing in the app, repo or site may identify the person who builds it** (Zewify rule; the Developer ID signature on the direct edition is the accepted exception).

## The download engine

A download is a URL plus the request context the browser handed over: referrer, cookies, user agent and any extra headers.
Every request the engine makes for that download carries that context, so a file behind a login downloads as the browser would have.

1. **Probe.** A `GET` with `Range: bytes=0-0` learns the size, whether the server honours ranges (`206` with `Content-Range`), the `ETag` or `Last-Modified` validator, the final URL after redirects, the content type, and the filename from `Content-Disposition` or the URL path.
2. **Plan.** A download with a known size, range support and at least 1 MiB is split into up to *n* segments of equal length, *n* from the gate (4 free, up to 32 Pro) and never more than size ÷ 512 KiB.
   Anything else is one segment and cannot resume.
3. **Fetch.** Each segment is a `URLSession` data task with `Range: bytes=<start+written>-<end>`, delivered incrementally through the session delegate, written at its own offset through its own `FileHandle` into `<folder>/<name>.haulpart`, which is preallocated to the full size.
4. **Rebalance.** When a segment finishes and another still has more than 2 MiB to go, the idle slot takes the second half of the largest remaining range, so the tail of a download runs as wide as its head.
   That is what IDM does, and it is the difference between a download manager and `curl`.
5. **Recover.** A segment whose connection drops retries from where it stopped, with backoff of 1, 2, 4, 8 and 16 seconds, five times per segment before the download fails.
   A `412` or a changed validator means the file changed on the server; the download restarts from zero.
6. **Finish.** When every segment is complete the part file is renamed to its final name; a name already taken becomes `name 2.ext`, `name 3.ext` and so on.

Progress is a snapshot struct — bytes received, total, per-segment written counts, a speed smoothed over the last three seconds and an ETA from it — published to the model about ten times a second.
Pausing cancels the tasks and keeps the segments; resuming re-plans from the segments' written counts.
Segment state is saved with the library every second while anything is active and immediately on pause, so a crash loses at most a second.

## The queue

The library holds every download in order.
The queue starts downloads in the order they were added, never more than the concurrency limit at once (2 free, 8 Pro), and a waiting download shows as *Queued*.
Pause All and Resume All act on everything active or queued.
Finished and failed downloads stay in the list as history until removed; removing one can also delete its file.

## The local server and the extension

`ExtensionServer` is an `NWListener` on `127.0.0.1:48512` (the port is a setting) speaking enough HTTP/1.1 for small JSON requests: a request line, headers, a body sized by `Content-Length`, and a JSON reply.
It never listens on any other interface.

| Route | Who | What |
|---|---|---|
| `GET /status` | anyone local | `{app, version, edition, features: {media}}`, so the extension knows the app is up and what it may offer. |
| `POST /pair` | an extension origin | The app asks the user to allow the browser, naming it; on *Allow* the reply carries the bearer token, otherwise `403`. The request waits up to 60 seconds for the answer. |
| `POST /downloads` | a paired extension | `{url, filename?, referrer?, cookies?, userAgent?, headers?}` becomes a download, through the catch panel if asking is on. Reply `201 {id}`. |
| `POST /media` | a paired extension, direct edition only | Like `/downloads` with `kind: "file"` or `"hls"`. The store edition answers `404`. |

Two checks guard every write: the `Origin` header must use an extension scheme (`chrome-extension://`, `safari-web-extension://`, `moz-extension://`), which a web page cannot forge, and after pairing the `Authorization: Bearer` token must match the one the app generated at first launch.
`/pair` only needs the first.

The extension, in `Extension/`, is Manifest V3 with a background service worker:

- **Capture (Chromium).** `downloads.onCreated` for an `http(s)` URL not started by the extension itself: if capture is on and the app answers `/status`, cancel and erase the browser's download, gather the site's cookies with the `cookies` API, and `POST /downloads`.
  If the app is not running the browser's own download proceeds untouched, so the extension never loses a file.
- **Capture (both).** A content script sends link clicks whose path ends in a known file extension (archives, disk images, installers, media, documents) to the app and cancels the click, because Safari has no `downloads` API.
- **Context menu.** *Download with Haul* on links, images, audio and video, and on the page for its URL.
- **Popup.** Connection state, the capture toggle, a *Connect to Haul* button when unpaired, and in the direct edition the media found on the current tab.
- **Media sniffing (direct edition).** Loaded only after `/status` reports `features.media`: `webRequest.onHeadersReceived` across all URLs records responses whose content type is audio, video, `application/vnd.apple.mpegurl`, `application/x-mpegurl` or `application/dash+xml`, or whose path ends in `.m3u8`, `.mpd`, `.mp4`, `.webm`, `.m4a` or `.mp3`, per tab, with the action badge counting them.
  Choosing one posts it to `/media`.

Pure logic the extension needs (what counts as a file link, how a response is classified, how a request body is built) lives in `Extension/lib/` and is tested with `node --test`; the background and content scripts stay thin.

## The video grabber (direct edition)

A `file` media item is an ordinary download.
An `hls` item is fetched by `HLSDownloader`: it reads the playlist with the download's request context; a master playlist resolves to its highest-bandwidth variant; the media playlist's segments are fetched a few at a time and appended in order to one file, `.ts` for MPEG-TS segments or `.mp4` when an `EXT-X-MAP` init segment is present, with AES-128 segments decrypted using the key URI and IV from `EXT-X-KEY`.
Progress counts segments.
Streams with DRM (`SAMPLE-AES`, Widevine, FairPlay) are declined with a clear message, and the app never promises any particular site.

## The app

- **Main window.** A toolbar with Add URL, Pause All and Resume All; a filter for All, Active, Done and Failed; a list where each row shows the file's icon, name, a segment map (one bar, each segment's filled part drawn in place, the signature of a segmented downloader), size, speed, ETA and state, with pause, resume, retry, cancel, Show in Finder, Open and Remove.
  Add URL takes a pasted URL or a list of them.
- **Catch panel.** A small floating window for a captured download: editable filename, folder, the probed size and type as soon as known, Start and Cancel.
  With asking off, downloads start straight away.
- **Menu bar item.** A ring showing combined progress while anything downloads; its menu lists the active downloads with progress, the combined speed, Pause All, Resume All, Open Haul and Quit.
- **Settings.** General: download folder, ask before starting, open at login, keep running when the window closes.
  Connections: connections per download, downloads at a time, the server port.
  Browser: connection state, paired browsers with a Forget button, and how to install each extension.
  Pro: the licence field (direct) or the purchase button (store, wired at launch time).
- **Pro and licences.** `FeatureGate` holds every free/Pro rule.
  The direct edition verifies an Ed25519 licence, `HAUL1-<payload>.<signature>`, offline against a public key in the app, as VoxMorph does; `licensetool` issues them.
  The store edition uses StoreKit the way TickThock does; wiring the product is launch work.
  `-HaulForcePro YES` unlocks Pro in Debug builds for testing.

## Error handling

- The app is not running: the browser downloads the file itself; the extension's icon shows it is disconnected.
- The port is taken: the server tries again every ten seconds and Settings says which process holds it.
- The server refuses ranges or hides the size: a single-connection download that cannot resume, labelled as such.
- The file changed on the server mid-download: restart from zero with a notice.
- The disk is full or the folder is not writable: the download fails with the system's message and the part file is left for retry.
- A segment's connection dies: retried with backoff; after five failures the download fails and can be retried by hand.
- The licence is malformed, forged or for another product: a specific message for each.

## Testing

- **Core tests** run against an in-process `NWListener` test server that serves a known blob with range support, and can be told to refuse ranges, hide the size, drop a connection after *n* bytes, or change its validator.
  They check that a segmented download is byte-identical to the blob, that pause and resume continue from the saved segments, that a dropped connection recovers, that rebalancing splits the largest remaining range, that the no-range path falls back to one stream, that the part file is renamed and collisions are numbered, the HTTP parser, the server's origin and token checks, pairing, the library's round trip, the gate, licences and the HLS parser.
- **App-hosted tests** cover the queue policy on `AppModel`.
- **Extension tests** (`node --test`) cover `Extension/lib/`.
- **End to end**, by hand or script: build the app, launch a separate Chrome with `--user-data-dir` and `--load-extension`, click a file link on a local test page, and watch the download arrive in the app.

## Out of scope for 1.0

The speed limiter, the scheduler, Firefox, categories and auto-sorting rules, FTP and BitTorrent, site logins stored by the app, and any transcoding.
